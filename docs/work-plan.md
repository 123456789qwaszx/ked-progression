# 작업 계획 — 시나리오 · 챕터 · 에피소드와 유저 데이터

기준: 2026-08-18 · 이 문서는 **순서·게이트·결정 대기**만 말한다.
**타입의 정본은 [`architecture.md`](architecture.md)다.** 모양을 여기에 복사하지 말 것.

> **목표 한 줄**
> 텍스트가 재생되는 것을 **게임 플레이로 잇는다.**
> 그 사이에 없는 것은 둘 — **시나리오 층**과 **유저 데이터.**

---

## 0. 범위 — 무엇이 문제가 아닌지부터

**텍스트 재생은 문제가 아니다.** `ked-presentation-runtime`이 `.yarn`에 텍스트를 넣으면
재생을 보장한다. 검증된 도구다. VnTool 출력이 안 맞으면 출력 양식만 바꾸면 된다.

이 저장소가 풀 문제는 재생이 아니라 그 **앞뒤**다:

| | 지금 | 필요한 것 |
|---|---|---|
| 재생 **전** | 어느 에피소드를 재생할지 아무도 모른다 | 그래프가 다음 노드를 정한다 |
| 재생 **후** | 끝나면 끝이다 | 스탯이 커밋되고 다음으로 넘어간다 |
| 챕터가 끝나면 | **아무 데도 안 간다** | 시나리오 층이 다음 챕터를 정한다 |
| 껐다 켜면 | **스탯이 사라진다** | 유저 데이터가 남는다 |

## 1. 실측 — 무엇을 참고했고 무엇을 안 가져오나

세 구현을 읽었다. **형태는 셋 다 비슷하고 규율이 갈렸다.** 상세는
[`architecture.md`](architecture.md) §0·§1.

| 출처 | 가져오는 것 | 안 가져오는 것 |
|---|---|---|
| 런타임 `EpisodeSelection` (test13) | `ChapterEndingRule`의 **모양** · Validator 403줄을 **명세로** | 코드 전부 — 평가기가 조용히 틀린다 |
| 런타임 `PresentationCore/Flow` | **원칙 넷** — 명시적 "없음"(`Immediately`) · 스펙/진행/인플라이트 3분할 · 계획 선확정 · 종료 방식 둘 | 코드 — 전역 네임스페이스 · SO 결합 · fallback 침묵 |
| VnTool `Vn.Authoring.Chapters` | 간선 관문(v8) · 스탯 경계 · 도달성 증명 | 엔진·엑셀 결합부 |

> ✅ **CHANGELOG 정정 완료.** *"`EndingRules`는 데이터에 모양이 없다"*는 판단의 전제가
> 틀렸다 — 런타임 `ChapterEndingRule`에 온전한 모양이 있고 툴이 안 낼 뿐이었다.
> **1:1로 받아 적지는 않았다**: `bool UnlockNextChapter`는 sentinel 쌍이라 빼고
> `EndingOutcome` 두 갈래로 바꿨다.

### ⚠ 유저 데이터의 현재 상태 — 2026-08-18 정정

전에는 *"`VNSaveData`는 저장되는데 `EpisodeSelectionStateData`는 메모리에만 있다"*로
적었다. **그건 `test13`(08-12 정지)의 그림이다.**

런타임의 mainline `dev`(08-17)를 실측하면 **둘 다 0파일**이다 — 진행·세이브·변수 저장소를
통째로 걷어냈다. `PresentationCore/Flow`도 `dev`에 없다(`phase2-*`·`test13`에만).

| | 뜻 |
|---|---|
| 원칙(P1·P3·P4) | **유효하다.** 읽고 배운 것이라 브랜치와 무관하다 |
| *"런타임에 이미 있으니 붙이면 된다"* | **거짓.** 그런 문장은 전부 다시 봐야 한다 |
| G4의 난이도 | 맞출 기존 모양이 없어 **쉬워지고**, 호스트 세이브 기반이 없어 **어려워졌다** |

마스터 플랜 §0-2의 *"Tier 2는 저장되고 챕터를 넘나든다"* 중 **"넘나든다"는 참이 됐고
"저장되고"는 여전히 거짓**이다.

## 2. ⛔ 소유자 결정 — 코드보다 먼저

전문은 [`architecture.md`](architecture.md) §6. 여기서는 **무엇을 막는지**만.

| | 결정 | 막는 것 |
|---|---|---|
| **D1** ✅ | 스탯 정의의 소유 | **시나리오.** 경계·타입은 갈리면 오류, 초기값은 증명 진입 가정이라 갈려도 된다 |
| **D2** ✅ | 엔딩을 무엇이 정하나 | **노드의 `EndingKey`.** 규칙은 그 키로 조회되는 표다 |
| **D3** ✅ | `Tokens` · `Flags` | **둘 다 안 넣는다** — 아이템·열쇠는 작가 계층의 Yarn 변수다(저작 쪽 확인) |
| **D4** | 세이브 스키마 버전 정책 | W7 |
| **D5** | 저작 `간선` 시트에 `종류` 열 | **막지 않는다** — 없어도 진행하되 사고 하나가 열린 채로 남는다 |

**D5가 미묘하다.** 지금은 문구가 비면 자동 진행으로 읽는다. 그래서 작가가 엑셀에서 선택지
문구를 실수로 지우면 **분기가 조용히 사라진다.** 모델은 `OptionKind`로 막지만, 데이터에
종류가 없으면 로더가 그 둘을 구별할 수 없다. 열을 안 둘 거면 **로더가 자동 진행 간선을
경고로 보고**하는 것이 차선이다.

## 3. 작업 목록

### 트랙 0 — 기존 타입을 원칙에 맞춘다 (`0.x`니까 지금이 가장 싸다)

| | 작업 | 근거 | 깨지나 |
|---|---|---|---|
| **W0a** | `ProgressionCondition` 생성자 → 팩토리 셋 · `ChapterCleared` 추가 | P1 · D3 | 테스트 (기계적) |
| **W0b** | `EpisodeOption` 생성자 → `Choice` / `Auto` | P1 — **문구 지움 사고** | 테스트 (기계적) |
| **W0c** | `EpisodeNode.IsChapterEndingCandidate` 제거 | sentinel 쌍 | 예 |
| **W0d** | `WithStatChanges` + `WithMovedTo` → `Commit` 하나 | P1 — **트랜잭션 경계의 타입 표현** | 예 |

> **W0d가 트랙 0의 핵심이다.** 두 메서드가 각각 public이면 따로 부를 수 있고, 따로 부를
> 수 있으면 언젠가 따로 불린다. 그 순간 "스탯만 바뀌고 안 옮겨 간" 상태가 생기는데 그게
> 정확히 §3.3이 막으려던 중복 가산이다. **합치면 그 상태가 존재할 수 없다.**

## 4. 순서와 게이트

```
   D1·D2·D3 결정 ──────────┐
                           │
   X1 (툴) ──────────┐     │
                     │     ▼
1주차   W0a~W0d ─────┼───► W1 ──► W2
        (원칙 정렬)  │      (시나리오 층)
                     ▼
2주차          W3 DTO·로더 ◄── 실제 툴 JSON
                     │
                     ├──► W4 챕터 전이
                     └──► W5 시나리오 전이
                            │
3주차                  W6 ──► W7  (유저 데이터)
                            │
4주차                  W8 증명 이관 (닫힘) ──► 챕터 연쇄(§9)
                            │
                            ▼
                       태그 `0.2.0`
```

| | 게이트 | 판정 |
|---|---|---|
| **G0** ✅ | 원칙이 타입에 들어갔다 | 무효 조합이 **컴파일되지 않는다** — 관문 달린 자동 진행, `EpisodeCleared + GreaterOrEqual`, 커밋 없는 이동 |
| **G1** ✅ | 시나리오가 선다 | 손으로 쓴 JSON(챕터 3개)이 오류 0으로 실린다 (`Tests/ScenarioProgressionTests.cs`) |
| **G2** ✅ | 실데이터가 실린다 | **툴이 낸 챕터 JSON**이 오류 0으로 로드되고, 시작에서 엔딩까지 걸어진다 (`Tests/RealExportLoadTests.cs`) |
| **G3** ✅ | 챕터가 이어진다 | ch01 끝 → 엔딩키로 갈려 ch02_trusted / ch02_plain. **스탯이 넘어간다** |
| **G4** | 껐다 켜도 같다 | 세이브 왕복 후 스탯·클리어 집합이 같다. 에피소드 ID 하나를 지우면 **진단이 난다** |
| **G5** ✅ | 증명이 같다 | 이관 전후 결과 일치 (`ReachabilityEquivalenceTests`) |

**G0이 이번 계획의 성격을 정한다.** "테스트가 통과한다"가 아니라 **"틀린 코드를 쓸 수 없다"**가
판정 기준이다. **G3이 전체를 증명한다** — 마스터 플랜 §0-2가 참이 되는 지점.

**뒤처질 때 버리는 순서**: W8 챕터 연쇄 → `Tokens` → 엔딩 이력 → W5의 조건부 간선.
**절대 안 버리는 것**: W0d · D1 · W7의 진단 · G3.

## 5. 매 작업 체크

원칙 전문은 [`architecture.md`](architecture.md) §1.

| | 이 계획에서 구체적으로 |
|---|---|
| **P1 불가능한 상태** | 무효 조합을 예외로 잡고 있으면, **타입으로 올릴 수 있는지 먼저 본다** |

| **P5 침묵 금지** | 진단이 자리를 짚는다. 잠긴 이유는 원인 조건을 지목한다 |

⚠ **함정 — 건드리지 말 것**: csproj의 `LangVersion 9.0` · `Nullable disable` ·
`ImplicitUsings disable`. dotnet 빌드를 유니티 빌드의 대역으로 만드는 장치다
(handoff §6-1). 켜는 순간 CI의 신뢰도가 사라진다.

## 7. 규모 — 미리 알아 둘 것

**스탯 범위는 콘텐츠 결정이 아니라 성능 결정이다.** 도달성 증명은 (에피소드 × 스탯 정수
벡터)를 완전 탐색하고, **챕터를 이으면 거기에 챕터 수가 곱해진다.**

| 스탯 | 범위 | 상태 수 |
|---|---|---|
| 2개 | 0..5 | 36 |
| 3개 | 0..10 | 1,331 |
| 5개 | 0..100 | 약 100억 — **증명기가 죽는다** |

넓혀 놓고 나중에 좁히면 이미 쓴 조건식이 전부 의미를 잃는다. **2~3개 · 0..5로 시작한다.**

## 9. 챕터 연쇄 증명 — 아직 결정이 남았다

증명 이관(W8)은 **챕터 하나** 단위로 닫혔다. D1이 그 위에 하나를 더 전제한다:

> ch01의 **출구 스팬**이 ch02의 **진입 가정**이 되어야 증명이 함께 이어진다.

지금 `ReachabilityResult.SpansFor(episodeId)`가 에피소드별 도착 폭을 낸다 — 재료는 있다.
남은 것은 **무엇을 진입 가정으로 삼을지**이고, 그게 자명하지 않다.

| 안 | 진입 가정 | 대가 |
|---|---|---|
| (가) 엔딩 노드들의 스팬 합집합 | 어느 엔딩으로 끝나든 가능한 폭 | 넓다 — 실제로 못 오는 조합까지 포함해 **과대근사**가 커진다 |
| (나) **엔딩키별** 스팬 | `ch01_good`으로 끝났을 때의 폭만 | 정확하다. 다만 시나리오 간선이 엔딩키로 갈리므로 **자연스럽게 맞는다** |
| (다) 전 경로 조합 탐색 | 정확 | 상태공간이 챕터 수만큼 곱해진다 — §7의 100억이 여기서 터진다 |

**(나)를 권한다.** 시나리오 간선이 이미 엔딩키로 갈리니(D2), 엔딩키별 스팬이 곧 그 간선의
진입 조건이 된다. 구조가 이미 그 모양이다.

⚠ 다만 (나)도 근사다 — 같은 엔딩키로 끝나는 서로 다른 경로의 폭을 합치기 때문이다.
**과대근사라는 방향은 유지되므로 "진짜 도달 불가를 놓치지 않는다"는 성질은 지켜진다.**

**언제 하나**: 챕터가 실제로 둘 이상 이어진 콘텐츠가 생긴 뒤. 지금은 손으로 쓴 시나리오
픽스처뿐이라, 만들어도 검증할 실물이 없다.

# 작업 계획 — 2기: 코어를 두 도구 사이에 끼운다

기준: 2026-08-21 · 이 문서는 **순서·게이트·결정 대기**만 말한다.
타입의 정본은 [`architecture.md`](architecture.md), 규칙의 정본은 [`principles.md`](principles.md),
호스트 쪽 설계는 [`host-integration.md`](host-integration.md). 모양을 여기에 복사하지 말 것.

> **1기(2026-08-17~20)는 닫혔다.** 게이트 G0~G5 전부 ✅ — 원칙이 타입에 들어갔고(G0),
> 손으로 쓴 시나리오와 툴이 낸 실제 JSON이 오류 0으로 실리며(G1·G2), 챕터가 엔딩키로
> 갈리고 스탯이 넘어가고(G3), 세이브가 왕복하며(G4), 도달성 증명이 이관 전후로 같은 답을
> 낸다(G5). 그 위에 `EpisodeFlow`가 섰다 — 에피소드 하나를 트랜잭션으로 굴리고 챕터 경계를
> 넘긴다. 1기의 상세는 git 이력과 `CHANGELOG.md`에 있다.
>
> **2기의 목표 한 줄: 이 코어를 아직 아무 호스트도 몰아 보지 않았다. 그것을 끝낸다.**

## 0. 진단 — 왜 "견본"처럼 보이는가

코어는 맞게 만들어졌다. 견본처럼 보이는 이유는 코어가 아니라 **그 바깥**이다:

| | 사실 | 뜻 |
|---|---|---|
| 1 | 유니티·VnTool 어느 쪽도 `Ked.Progression`을 참조하지 않는다 (2026-08-21 실측, 두 저장소 grep 0건) | 공유된 것은 아직 **의도**이고 **코드**가 아니다 |
| 2 | 문서가 *왜*는 충분히 말하고 *어떻게 모는가*는 테스트에만 있었다 | 호스트 작업자가 읽을 것이 없었다 → `host-integration.md` |
| 3 | 원칙 태그(P·D)의 정의가 `architecture.md` 안에 흩어져 있어 리뷰어가 "정의 없음"으로 읽었다 | → `principles.md` 한 장 |
| 4 | 계약 칸 하나(`StatChange` 지정)가 비어 **깃발을 쓰는 챕터가 내보내기 거부**된다 | 실콘텐츠가 코어에 닿기 전에 막힌다 → C1 |
| 5 | 툴이 시나리오를 저작하지 않아 유니티가 시나리오 없이 챕터를 못 돈다 | → C2 |

**4와 5가 실제 차단 항목이다.** 나머지는 문서였고, 이번에 닫았다.

## 1. 트랙 C — 코어 (2기에서 코어가 바뀌는 것은 이것뿐이다)

`0.x`라 지금이 가장 싸다. 단, **호스트를 붙이기 전에 끝낸다** — 붙인 뒤에 DTO를 바꾸면 두 호스트가 같이 움직여야 한다.

| | 작업 | 왜 | 깨지나 |
|---|---|---|---|
| **C1** ⛔ | `StatChangeDto.Op` (`"Add"` 기본 / `"Set"`) · `StatChange.Kind` · 불변식 셋(`Set`은 Bool에만 · 값 0/1 · 한 간선에 같은 키 두 번 금지) · `Commit`과 `ChapterReachability`의 적용이 지정에서는 현재 값을 보지 않음 | 저작 쪽은 끝났다(`java-start/docs/work-orders/bool-stat-orders.md`). 이 칸이 없으면 깃발을 쓰는 챕터는 파일이 안 나간다. **유일한 차단 항목** | DTO 추가뿐. 기존 파일은 한 글자도 안 바뀐다. 코퍼스 7케이스에 지정이 없어 기존 답 불변 — 깃발 케이스 하나를 저작 쪽에서 떠 받는다 |
| **C2** | `ProgressionLoader.LoadAsSingleChapterScenario(ChapterProgressionDto)` — 챕터 하나를 규칙 0개 시나리오로 감싼다. 챕터 `Stats`가 시나리오 것이 된다 | 시나리오 저작(X4) 전에 유니티가 돌아야 하고, 그 뒤에도 "챕터 하나만 테스트 플레이"는 영원히 필요하다 | 추가뿐 |
| **C3** ✅ | `EpisodeFlow` 문서화 — `architecture.md` §2.9·§2.10 | 1기 끝에 들어가 문서에 없었다 | — |
| **C4** | `ChapterProgression.CreateInitialState()` → **`CreateProofEntryState()`** 로 개명 | 시나리오 것과 이름이 같아 잘못 부르면 **예외 없이 다른 플레이가 조용히 시작**된다(handoff §5-6). 이름으로 가른다 — P1의 정신 | 테스트 (기계적) |
| **C5** | `0.2.0` 태그 | 소비자가 가져갈 만해졌다. **`.meta`가 먼저다** — 태그 뒤에 `.meta`를 넣으면 그 태그는 쓸모가 없다 | — |

**C1 → C2 → C4 → (유니티에서 `.meta` 생성) → C5** 순서. 전부 합쳐 하루 일이다.

## 2. 트랙 H — 유니티 호스트 (우선)

상세 설계는 `host-integration.md` §2·§3·§6. 여기는 순서와 판정만.

| | 작업 | 완료 기준 |
|---|---|---|
| **H0** | C2 + 손으로 쓴 `scenario.json` 중 하나로 **챕터 하나가 시나리오로 선다** | `ProgressionLoader`가 진단 0 |
| **H1** | U-0 · U-1 · U-2 — UPM 참조, `StartGameAsync` 결과 반환, `ProgressionDriver` | `ch01.progression.sample.json`이 유니티에서 **시작 → 선택 → 엔딩**까지 걸어진다. 선택지는 임시 UI여도 된다 |
| **H2** | U-3 — 에피소드 선택지 뷰 (`Locked` + 사유 표시, 배열 순서) | 잠긴 선택지가 **회색으로 보이고 이유가 뜬다.** 숨은 것은 안 보인다 |
| **H3** | U-4 · U-5 — 세이브 블록 합성, 타이틀에서 이어 하기 | 에피소드 경계에서 저장 → 종료 → 이어 하기 → **같은 에피소드에서 같은 스탯으로** 계속. 콘텐츠에서 에피소드를 지운 뒤 로드하면 **거부**된다 |
| **H4** | `ViaNodeId`가 실린 표본으로 연출 재생 | 간선을 지날 때 `PlayVia` 노드가 재생되고 그 뒤 커밋된다 |

**H1이 2기 전체를 증명한다** — "툴이 만든 데이터를 유니티가 재생한다"가 대사 층에서
참이었던 것이 진행 층에서도 참이 되는 지점. 설계 리뷰가 "미수금"이라 부른 것이 여기서 현금이 된다.

## 4. 순서와 게이트

```
 C1 StatChange.Set ──► C2 단일챕터 ──► C4 개명 ──► [.meta] ──► C5 0.2.0
        │                   │
        │                   └──► H0 ──► H1 ──► H2 ──► H3 ──► H4     (유니티)
        │                              │
        └──────────────────────────────┴──► T1 ──► T2 ──► T3 ──► T4 ──► T5   (VnTool)
                                                              │
                                                   X3 · X2 · X4 (툴 저작 확장)
```

| | 게이트 | 판정 |
|---|---|---|
| **H1** | 유니티가 코어를 몬다 | 툴이 낸 JSON이 유니티에서 시작→엔딩까지 걸어진다 |
| **H3** | 껐다 켜도 같다 (실기) | 진행 블록 + 대사 블록 합성 세이브로 이어 하기 |
| **T3** | 구현이 하나가 됐다 | 옛 증명기와 코어의 답이 모든 입력에서 같다 → 옛 것을 지운다 |

## 5. 트랙 E — 표현력 (설계 리뷰 §7·§8을 실측과 대조한 것)

리뷰가 짚은 갭 다섯과 그에 대한 이쪽 판단. **전부 2기 비범위**다 — 실제 작품 한 챕터를
포팅해 봐야 진짜 갭이 나온다(리뷰 §8 "검증 — 설계보다 먼저"에 동의). 다만 **스키마와
소유권을 건드리는 것은 미리 선을 그어 둔다.**

| # | 갭 | 판단 | 언제 |
|---|---|---|---|
| 1 | 회차 계승 상태 (`EndingSeen`) — 계정 단위 | **소유권 선은 이미 그었다**: 전역 진행은 슬롯 세이브가 아닌 별도 저장이고, 전역 조건은 **시나리오 층 간선에만** 허용(양쪽 합의). 타입은 엔딩이 실제로 서너 개 생긴 뒤 데이터에서 뽑는다 | 앨범이 필요해질 때 |
| 2 | `NotExists` | bool 도메인이라 구간 전파가 안 깨진다. **저작 파서가 먼저 열어야 한다** — 닫힌 채로 코어에 넣으면 영원히 안 타는 분기(`NotEqual`과 같은 판단) | 저작이 열 때 같이 |
| 3 | 방문 횟수 (`ClearedEpisodeIds` → `VisitCounts`) | 상위 호환이고 구간 전파를 그대로 쓴다는 리뷰 판단에 동의. 다만 **지금 아무 소비자가 없다.** D4가 버전 올림을 싸게 만들어 두었으므로 재방문 콘텐츠가 생길 때 `SchemaVersion 2`로 한다 | 재방문 콘텐츠가 생길 때 |
| 4 | 스탯 간 비교 | 도달성에서 `Unknown`. 도입하면 툴이 "검증 커버리지 %"를 노출해야 한다 — 그 UI가 먼저다 | 브란테식 포팅이 요구할 때 |
| 5 | 난수 | 시드를 `ProgressionState`에, PRNG를 코어 안에. `UnityEngine.Random`을 쓰는 순간 전부 날아간다 | 텍스트RPG 포팅이 요구할 때 |

**넓힐 때마다 `principles.md` §6의 표를 채운다.** 세 소비자(평가기·로더·분석기) 중 누가
감당하고 못 하는 쪽은 그것을 어떻게 드러내는가. 답 못 하면 보류.

## 7. 챕터 연쇄 증명 — 결정이 남았다 (1기에서 이월)

증명은 챕터 하나 단위로 닫혔다. D1이 그 위에 하나를 더 전제한다: ch01의 **출구 스팬**이
ch02의 **진입 가정**이 되어야 증명이 함께 이어진다. 재료(`ReachabilityResult.SpansFor`)는 있다.

| 안 | 진입 가정 | 대가 |
|---|---|---|
| (가) 엔딩 노드들의 스팬 합집합 | 어느 엔딩이든 가능한 폭 | 과대근사가 커진다 |
| (나) **엔딩키별** 스팬 | `ch01_good`으로 끝났을 때의 폭만 | 시나리오 간선이 엔딩키로 갈리므로(D2) 구조가 이미 이 모양 |
| (다) 전 경로 조합 탐색 | 정확 | 상태공간이 챕터 수만큼 곱해진다 — §8의 100억 |

**(나)를 권한다.** 과대근사 방향은 유지되어 "거짓 경보 없음"이 지켜진다.
**언제**: 챕터가 실제로 둘 이상 이어진 콘텐츠가 생긴 뒤(X4 이후).

## 8. 규모 — 기획자에게 전달되어야 하는 것

증명은 (에피소드 × 스탯 정수 벡터)를 완전 탐색한다. **스탯 범위는 콘텐츠 결정이 아니라 성능 결정이다.**

| 스탯 | 범위 | 상태 수 |
|---|---|---|
| 2개 | 0..5 | 36 |
| 3개 | 0..10 | 1,331 |
| 5개 | 0..100 | 약 100억 — 증명기가 죽는다 (`StateLimit = 250_000`) |

**2~3개 · 0..5로 시작한다.** 넓혀 놓고 나중에 좁히면 이미 쓴 조건식이 전부 의미를 잃는다.

## 1. `Option.ViaNodeId` — 이미 있다

`eb1786d` "연출을 매다는 자리". 그쪽 문서가 쓰인 시점보다 앞선다.

```json
{
  "TargetEpisodeId": "믿는길",
  "ChoiceLabel": "라루를 믿는다",
  "ViaNodeId": "fade_trust",
  "StatChanges": [ { "Key": "trust", "Amount": 2 } ]
}
```

| | |
|---|---|
| 이름 | **`ViaNodeId`** — 계약서 §H-3 그대로 |
| 자리 | `NextOptions`의 각 간선. **자동 진행 간선에도 붙는다** |
| 값 | 이름 하나. 비면 곧장 간다 |
| 이쪽이 하는 일 | **없다.** `DialogueEntryId`와 같은 종류의 통과값이라 내용을 모른다 |

### ⚠⚠ 이름 번역 — 조용히 사라지는 자리

그쪽 모델은 `ChapterEdge.PresentationNodeName`인데 **JSON 키는 `ViaNodeId`**다.

`PresentationNodeName`으로 내보내면 역직렬화기가 **모르는 속성을 기본으로 무시**하므로
이쪽 값이 빈 문자열로 남는다 — **오류 하나 없이 연출만 사라진다.**
그쪽의 "연출이 아직 비어 있습니다" 경고도 못 잡는다: 그건 모델을 보는 검사이고
모델에는 값이 멀쩡히 있다.

`Int → "Number"` · `AtLeast → "GreaterOrEqual"`과 같은 자리다.
**내보내기 테스트에 키 이름을 문자로 박아 두면** 닫힌다.

```csharp
Assert.Equal("fade_x", option.GetProperty("ViaNodeId").GetString());
```

### ⚠ 여기에 파라미터를 붙이지 말 것

지속시간·이징·색이 들어오기 시작하면 그때가 경계면이 진짜로 넓어지는 순간이다.
**연출의 파라미터는 연출 쪽에서 산다.** 이쪽 테스트가 그 칸이 문자열임을 붙들고 있다.

## 2. `EndingRules` — 모양은 정해져 있다. 이쪽이 대기하는 게 아니다

그쪽 §7의 이 문장을 정정한다:

> *"이 엔딩이면 다음 챕터는 무엇" 규칙을 **지금은 아무도 안 들고 있다.**"*

**이쪽이 들고 있다.** `EndingRule` · `ScenarioProgression` · `ScenarioTransition`이 있고,
손으로 쓴 시나리오 픽스처(챕터 3개)로 실제로 돈다 — 엔딩키에 따라 다음 챕터가 갈리고
스탯이 넘어간다. **툴이 안 낼 뿐이다.**

```json
"EndingRules": [
  {
    "Outcome": "NextChapter",
    "EndingKey": "ch01_true",
    "DisplayName": "함께",
    "NextChapterId": "ch02_together",
    "Conditions": [ { "Kind": "Stat", "Key": "trust", "Op": "GreaterOrEqual", "IntValue": 2 } ]
  },
  { "Outcome": "NextChapter", "EndingKey": "ch01_true", "NextChapterId": "ch02_plain", "Conditions": [] }
]
```

### 반드시 지켜야 하는 것 넷

1. **`Outcome`을 명시 문자열로 낼 것** — `"NextChapter"` / `"ScenarioEnd"`.
   `NextChapterId`가 비었는지로 판별하지 않는다. 그러면 *"여기서 끝난다"*와
   *"다음을 실수로 안 적었다"*가 **같은 모양**이 된다 — 선택지 문구가 비면 자동 진행이던
   것과 같은 사고다
2. 엔딩키를 내는 노드에는 **그 키의 규칙이 있어야 한다** (엔딩인데 갈 곳이 없으면 안 된다)
3. **아무도 안 내는 키의 규칙은 오류다** (영원히 안 타는 분기)
4. 같은 키의 **마지막 규칙은 조건이 없어야 한다** — 전부 미달일 때 무슨 일이 일어나야
   하는지 아무도 안 적으면 런타임이 추측하게 된다

⚠ 규칙이 **하나도 없는** 챕터는 정상이다(단일 챕터에서는 엔딩이 곧 종착). 2번은 규칙이
하나라도 있을 때만 본다 — **그래서 지금처럼 빈 배열로 내도 아무것도 안 깨진다.**

**엔딩을 정하는 것은 노드다(D2).** 규칙의 `Conditions`는 엔딩을 판정하지 않고, 같은 키에서
다음 챕터가 갈릴 때 갈래를 고른다.

## 3. 도달성 증명 — 이관 끝. **그쪽에 새 의무가 하나 생겼다**

`ChapterReachabilityProver`를 옮겼다. 판정 기준대로 **알고리즘을 개선하지 않고 그대로**
옮겼다 — 더 나은 방법이 몇 군데 보였지만 등가성이 먼저다.

등가성은 주장이 아니라 **코퍼스**로 고정했다. `java-start`에서 **그쪽 증명기를 그대로 돌려**
케이스 일곱(직선 · 분기수렴 · 관문 · 도달불가 · `cleared:` 고정점 · 부착 · clamp)마다
내보낸 챕터 JSON과 그때의 결과를 한 벌로 저장했고, 이쪽 테스트가 매번 **도달 가능 집합 ·
완전 탐색 여부 · 에피소드별 스탯 폭** 셋을 대조한다.

> 뽑은 시점은 `ChapterReachabilityProver.cs`가 아직 안 건드려진 때다.
> **기준선은 흔들리기 전에 박아야 했다.** 임시 생성기는 뽑고 지웠다.

### ⚠ 그래서 그쪽 증명기는 이제 **고정된 오라클**이다

동작을 바꾸면(버그 수정 포함) **두 구현이 조용히 갈린다.** 이쪽 코퍼스는 옛 답을 들고 있고,
이쪽 테스트는 계속 초록이다 — 갈렸다는 것을 아무도 모른다.

**바꿀 때 알려 주면 된다.** 코퍼스를 다시 뽑고 차이를 대조해 양쪽을 함께 맞춘다.
캐시(내용해시 → 결과)는 화면의 사정이라 상관없다.

### 이관하며 더한 것 하나

`ChapterCleared`를 **진입 가정으로 받는 인자**. 그쪽은 챕터 단위로만 증명해서 없던 것이고,
비우면 아무것도 안 바뀌므로 등가성에 영향이 없다.

### 챕터 연쇄는 아직 안 했다

D1이 *"ch01 출구 스팬 → ch02 진입 가정"*을 전제하는데, **무엇을 진입 가정으로 삼을지**가
아직 결정이다(안 셋과 권고는 이쪽 `work-plan.md` §9). 재료인 에피소드별 스탯 폭은
그쪽 `StatSpans`를 그대로 옮겨 이미 나온다. **콘텐츠가 실제로 둘 이상 이어진 뒤에 한다.**

## 4. 유저 데이터(G4) 닫힘 — 다만 **앨범은 다른 저장 범위다**

세이브를 굽고 되살린다. 어려운 것은 직렬화가 아니라 **어제 콘텐츠로 저장하고 오늘
콘텐츠로 여는 것**이었고, 규칙은 이렇다:

| | |
|---|---|
| 새로 생긴 스탯 | 초기값으로 채운다 — **조용해도 되는 유일한 경우** |
| 정의에 없는 스탯 · 경계 밖 값 | 버리거나 자르고 **경고** |
| 사라진 클리어 기록 | 버리고 경고 — **그것을 보던 관문이 다시 잠긴다** |
| 사라진 챕터·에피소드 · 다른 시나리오 · 더 높은 스키마 버전 | **오류. 상태를 안 만든다** |

### 앨범이 여기 안 들어가는 이유

세이브가 하나가 아니라 **둘**이다.

| | 담는 것 | 언제 초기화 |
|---|---|---|
| **슬롯 세이브** (`ProgressionSave`) | 지금 어디까지 왔나 — 챕터·에피소드·스탯·클리어 | 새 게임마다 |
| **전역 진행** (아직 없음) | 무엇을 **본 적 있나** — 엔딩·CG·기읽은 줄 | **안 된다. 판을 넘는다** |

앨범은 후자다. 그쪽이 *"엔딩 목록이 곧 앨범이지만 도달했나는 플레이어 데이터"*라고
적은 그대로이고, **그 '도달했나'가 슬롯이 아니라 전역에 산다.** `test13`의
`VNGlobalProgressData`(`unlockedEndingKeys` · `unlockedCgKeys` · `readLineIds`)가 그 모양이었다.

→ **자리를 안 만든 그쪽 판단이 맞다.** 엔딩이 실제로 서너 개 생긴 뒤에 스키마가
데이터에서 나오는 편이 낫다. 그리고 전역 진행은 *추가*가 안전한 종류라 미뤄도 싸다.

⚠ 하나만 미리 정해 두면 좋겠다 — **전역 조건(`EndingSeen`)을 챕터 안 간선에 허용하지 말 것.**
시나리오 층 간선에만 두면 증명이 전역 상태를 인자로 받아 한 번 탐색하면 되지만, 챕터
안까지 열면 상태공간이 **(한 판 × 전역 이력)**으로 곱해진다. §6의 100억이 거기서 터진다.

## 5. 2차 표본 — 받았다. 두 엔딩 다 걸어진다

`ch01.progression.sample.json`을 그대로 픽스처로 받아
(`Tests/Fixtures/chapter-ch01-sample.json`) 전이기를 거쳐 실제로 걸어 봤다.

```
시작 ─[라루를 믿는다]→ 믿는길 ─(자동)→ 좋은끝     → ChapterEnded("ch01_true")
   └─[혼자 간다]────→ 혼자길 ─(자동)→ 쓸쓸한끝   → ChapterEnded("ch01_alone")
```

오류 0. **엔딩키가 실제로 실려 왔다는 것이 실물로 확인됐다.**

> *"남에게 건넨 표본이 낡는 것은 계약서가 낡는 것과 같은 무게"* — 동의한다.
> 1차 표본이 낡은 채 이쪽 픽스처로 박혀 있었고, 그쪽이 갱신하지 않았다면
> **이쪽 테스트는 초록인데 계약은 갈려 있었을 것이다.** `ProgressionSampleGoldenTests`가
> 그것을 막는다.

### 확인해 준 것 둘

**`IsChapterEndingCandidate`와 `EndingKey`가 같다** — 그 말을 믿는 게 아니라 **로더가
불일치를 오류로 잡는다.** 둘 중 하나만 봐도 된다는 서술이 맞고, 어긋나면 파일이 안 실린다.

**엔딩 에피소드에 `NextOptions`가 있어도 된다** — *"끝날 수 있는 곳이지 막다른 곳이
아니다"*가 이쪽에서 도는 방식과 정확히 맞는다. 나가는 길이 있고 고를 수 있으면 계속
가고, 고를 수 있는 것이 하나도 없을 때 `ChapterEnded`가 되며 그때 그 노드의 엔딩키가 쓰인다.
관문이 전부 잠긴 엔딩 노드는 **거기서 끝난다** — 조건부 종착이 그렇게 표현된다.

## 6. 규모 — 다시 한 번

증명은 (에피소드 × 스탯 정수 벡터)를 완전 탐색하고, **챕터를 이으면 챕터 수가 곱해진다.**

| 스탯 | 범위 | 상태 수 |
|---|---|---|
| 2개 | 0..5 | 36 |
| 3개 | 0..10 | 1,331 |
| 5개 | 0..100 | 약 100억 |

넓혀 놓고 나중에 좁히면 이미 쓴 조건식이 전부 의미를 잃는다. **기획자에게 전달되어야 한다.**

# Ked.Progression 설계 리뷰

> 순수 C# 진행(progression) 코어에 대한 아키텍처 리뷰 요약.
> 대상: `Ked.Progression` / `Ked.Progression.Dto` — 24개 파일, 약 220K.

---

## 0. 배경

| 항목 | 내용 |
| --- | --- |
| 저작 툴 | Avalonia (구현 완료) |
| 런타임 | 유니티 비주얼 노벨 재생기 |
| 대사 층 | 별도 (코어는 이름만 안다) |
| 현재 | 선형 VN |
| 기획 방향 | 일본식 분기 VN / 브란테식 텍스트RPG / 혹은 전부 |
| 이 패키지의 목적 | 분기·조건·에피소드·엔딩의 **모양새 검증**과 범용성 확보 |

코어를 순수 C#으로 분리한 진짜 이유는 "엔진을 갈아탈지도 몰라서"가 아니라,
**저작 툴과 런타임이 같은 판정기를 공유하기 위해서**다. 이건 가상의 이유가 아니라
오늘 당장의 이유이고, 그래서 이 분리는 사치가 아니라 정답이다.

## 1. 코드에서 확인한 사실

- `UnityEngine` 참조 **0개**. `using`은 `System`, `System.Collections.Generic`뿐.
- 비결정성 **0개**: `DateTime.Now`, `Random`, 가변 static 없음
  (유일한 static은 `ChapterTransition`의 빈 배열 하나).
- 인터페이스·콜백·이벤트·`async` **0개**.
- `ProgressionLoader.Load`는 JSON 문자열이 아니라 **DTO**를 받는다.
- `ProgressionSaveDto`에 직렬화 어트리뷰트가 **하나도 없다**.
- `SchemaVersion`이 **처음부터** 들어 있다.
- `throw` 51개 — 전부 런타임 쪽. 로더는 진단 목록을 반환한다.

## 2. 왜 이것이 "코어"로 동작하는가

### 2.1 의존 화살표가 하나뿐이고 인터페이스조차 없다

보통의 "코어 분리"는 코어에 `IDialoguePlayer` 같은 인터페이스를 둔다.
그러나 인터페이스도 결국 코어가 호스트의 *모양*을 아는 것이다. 시그니처는
코루틴 기반이나 async 기반 중 한쪽으로 기울고, 다른 쪽이 어댑터를 덧대게 된다.

여기는 그 문제 자체를 없앴다 — 코어가 요구하는 계약이
**호출 가능한 무엇**이 아니라 **읽을 수 있는 값**이다.

### 2.2 제어를 역전한 게 아니라 반납했다 (Pull 모델)

코어는 아무것도 부르지 않는다. `Pending`에 "지금 대사 X를 재생하라"를
값으로 내놓고 **멈춘다**. 호스트가 제 방식대로 처리하고 완료를 알리면 진행한다.

이것이 만드는 독립성의 실체는 **코어가 시간을 소유하지 않는다**는 것이다.

- 콜백 없음 → "어느 스레드에서 불리나"가 없다
- `async` 없음 → 동기화 컨텍스트가 없다
- 이벤트 없음 → 구독 해제 타이밍이라는 생명주기 문제가 없다

유니티의 프레임 루프와 Avalonia의 디스패처는 완전히 다른 시간 모델인데,
코어가 둘 다 모르기 때문에 둘 다에 붙는다. `PlayDialogue`가 실제로 3초 걸리든
에디터 미리보기에서 0초에 스킵되든 코어에겐 구별이 없다.

`FlowRequestKind` 다섯 개(`PlayDialogue`, `PresentOptions`, `PlayVia`,
`PersistSave`, `Finished`)가 **외부 연결점의 전부**다.
경계면이 enum 하나로 열거 가능하다는 것이 "코어로 동작 가능"의 정량적 증거다.
대부분의 코드베이스는 자기 경계면을 열거하지 못한다.

### 2.3 판정이 순수 함수다 — 그래서 공유된다

```
ConditionEvaluator.IsMet(condition, state) → bool
ChapterTransition.Resolve(chapter, state)  → ChapterAdvance
```

둘 다 `static`, 입력 둘에 출력 하나, 부수효과 없음.
`ProgressionState`는 내부를 `IReadOnly`로만 노출하고 `ProgressionCondition`은
`readonly struct`다. 같은 입력이면 언제 어디서 몇 번을 불러도 같은 답이다.

순수 함수는 **호출자가 누구인지에 대한 가정이 없다.** 그래서 소비자 넷이
문자 그대로 같은 static 메서드를 부른다:

| 소비자 | 용도 |
| --- | --- |
| 유니티 런타임 | 실제 플레이 판정 |
| Avalonia 툴 | "이 상태면 뭐가 보이지?" 미리보기 |
| `ChapterReachability` | 정적 도달성 분석 |
| 유닛 테스트 | 검증 |

판정 로직이 두 벌이 되어 미묘하게 어긋나는 사고는 **구조적으로 불가능**하다.

### 2.4 변이의 문이 봉인돼 있다

상태가 바뀌는 자리는 `Commit`과 `CommitChapterEnding` 둘뿐이고,
그나마 변이가 아니라 **새 상태 생성**이다(불변).
생성자는 private, `FromSave`는 internal — 상태가 태어나는 길이
`CreateInitial` / `Commit` / `Restore` 경유 셋으로 **타입 시스템 수준에서 봉인**됐다.

그래서 안쪽 함수에 방어 코드가 없는 것은 게으름이 아니라,
**유효하지 않은 상태를 만들 방법이 없어서**다. 검증은 경계에서 한 번,
안쪽은 전제를 다시 묻지 않는다(P2).

### 2.5 판정과 실행의 시간 분리 (P4)

`Resolve`가 선택지 목록을 값으로 고정 → 플레이어가 10분 고민해도 상태는 불변 →
`Choose`는 이미 판정된 목록에서 고르기만 한다.
화면에 뜬 것과 실제 일어나는 일이 갈릴 틈이 없다.

### 2.6 경계 밖 관심사는 전부 이름으로 격하됐다

대사는 `DialogueEntryId`, 연출은 `ViaNodeId` — 코어는 Yarn을 모르고 **이름만** 안다.
세이브는 DTO를 굽기만 하고 파일 IO는 호스트 몫이다.
경계를 건너는 건 언제나 **이름과 값**이지 동작이 아니다.

> `FlowRequest` 주석: "지속시간·이징·화자가 여기 붙기 시작하면
> 그때가 경계면이 진짜로 넓어지는 순간이다."

## 3. 근본 모델

**"진행이란 게이트 달린 그래프 위의 결정적 전이 시스템이다."**

- **구조는 그래프** — 노드(에피소드) + 간선(옵션).
  조건과 효과를 노드가 아니라 **간선이 소유**한다.
  이 결정 하나로 "같은 곳으로 가되 조건이 다른 길"이 가능해졌고,
  분기 표현력의 대부분이 여기서 나온다.
- **층위는 셋** — 에피소드 → 챕터(엔딩키로 닫힘) → 시나리오(엔딩 규칙으로 연결).
  각 층의 끝맺음이 명시적 타입(`EndingRule`, `ScenarioAdvance`)이다.
  "빈 문자열이면 끝" 같은 암묵 규약이 없다.
- **상태는 불변 값** — 스탯 + 클리어 집합 + 엔딩 이력.
  전이가 순수 함수이므로 사실상 `초기상태 + 선택 목록 = 현재상태`라는
  이벤트 소싱적 성질을 갖는다. 재현성과 세이브 검증이 전부 여기서 나온다.
- **경계는 이름** — 대사·연출은 문자열 키로만 존재.

## 4. 설계 규칙 (코드 주석 태그에서 복원)

### P 계열 — 런타임 원칙

| 태그 | 내용 |
| --- | --- |
| P2 | 검증은 경계에서 한 번, 안쪽은 전체 함수. 안쪽에 방어 코드가 생기면 경계가 샌 신호. |

| 태그 | 내용 |
| --- | --- |
| 규율 2 | DTO는 어트리뷰트도 직렬화기도 갖지 않는다. 직렬화 기술은 호스트 소관. |
| 규율 4 | 판정은 순수 함수, 상태는 불변 — 바꾸지 않고 새 상태를 돌려준다. |

### 관통하는 메타 규칙

> **"모든 것에 주인이 하나다."**
> 스탯 변이는 간선만, 엔딩키는 노드만, 초기화는 시나리오만,
> 파일 IO는 호스트만, 검증은 경계만.

버그 추적이 빠른 코드베이스의 공통점이 정확히 이것이다.

> ⚠️ **P1, P5, D3, D5, §G9는 코드에 태그로만 등장하고 정의가 보이지 않는다.**
> 원칙 문서가 별도로 있다면 **코어와 같은 리포, 같은 커밋**에 두어야 한다.
> 규범 문서가 코드와 떨어지면 6개월 뒤 합류한 동료에게 이 태그들은
> 해독 불가한 암호가 되고, 그 순간부터 규칙은 지켜지는 게 아니라
> 우연히 유지되는 것이 된다.

## 5. 구조상 특징 — 9포인트

1. **의존 화살표 단방향, 인터페이스 0개.** 계약이 "호출 가능한 것"이 아니라 "읽을 수 있는 값".
2. **Pull 모델.** 경계면이 enum 하나로 열거된다. 코어가 시간을 소유하지 않는다.
3. **판정 = 순수 static 함수.** 소비자 넷이 한 벌을 공유. 판정이 갈라지는 사고가 불가능.
4. **상태 생성 경로 봉인.** 유효하지 않은 상태를 만들 방법이 없다.
5. **판정과 변이의 시간 분리(P4).** 표시된 것과 일어나는 것이 갈릴 틈이 없다.
6. **저장 최소주의(P3).** 세이브 호환성 부담이 최소로 유지된다.
7. **조건 언어가 평면 AND.** 이 좁음이 도달성 분석을 성립시킨다(§6 참조).
8. **이원 오류 계약.** 저작 오류는 진단 목록으로, 프로그래밍 오류는 throw로.
9. **완전한 결정성.** 세이브 하나로 버그가 재현되고, Domain Reload를 꺼도 안전하다.

## 6. 핵심 트레이드오프: 표현력 vs 정적 분석

`ChapterReachability`는 `minSeen`/`maxSeen` **구간 전파(interval propagation)**로
조건 충족 가능성을 판정한다. 이것이 가능한 이유는 조건이
`(Kind, Key, Op, 상수)` 평면 구조이고 **AND로만 묶이기 때문**이다.

| 추가하려는 표현 | 분석에 미치는 영향 |
| --- | --- |
| `OR` | 구간이 합집합이 되어 전파가 지수적으로 갈라진다 |
| 스탯 간 비교 | 축별 독립 구간으로 표현 불가. 관계 도메인이 필요 |
| 난수 | 도달성 자체가 확률 명제가 된다 |

> **조건 언어의 표현력과 정적 분석 가능성은 반비례한다.**

지금 모델이 좁아 보이는 건 실력 부족이 아니라, 좁혀야 툴이
"이 에피소드는 어떤 경로로도 도달 불가"라고 **단언**할 수 있어서다.
그리고 분기가 복잡해질수록 그 단언의 가치는 **올라간다** —
선형 VN은 눈으로 봐도 알지만 브란테 규모는 툴이 아니면 아무도 모른다.
기획이 복잡성을 원한다면, 역설적으로 조건 언어는 더 지켜야 한다.

**근사 방향이 옳다.** min/max를 축별 독립 추적하므로 **과대근사**이고,
따라서 "도달 불가"라고 말하면 진짜 도달 불가다(거짓 경보 없음).
툴이 신뢰를 잃지 않는 방향이다.

> 🔒 **불변식**: 앞으로 무엇을 추가하든 "거짓 경보 없음"은 깨지 않는다.

### 그럼에도 데이터 모델은 넓혀도 보존된다

제약은 **데이터 모델의 것도, 런타임의 것도 아니라 소비자 하나의 것**이다.

| 소비자 | 표현력 확장에 대한 민감도 |
| --- | --- |
| 런타임 평가기 | 거의 무관. `switch`에 case 추가면 끝 |
| 로더/인바리언트 | 정합성 검사가 조금 늘 뿐 |
| 도달성 분석 | **여기만 민감** |

순수 함수 구조 덕에 소비자들이 서로를 모르므로, **소비자마다 감당 범위가 달라도 된다.**
모델에 OR을 넣으면 런타임은 전부 실행하고, 분석기는 아는 부분집합에만
강하게 말하고 나머지엔 `Unknown`을 붙인다.
모델이 깨지는 게 아니라 **분석 커버리지가 줄어드는** 것이다.

단, "제한을 무시한다"에서 무시되는 건 분석기의 사정이지 제한이 사라지는 게 아니다.
**분석 가능성은 분석기 코드의 성능이 아니라 모델의 형태에서 나오는 성질**이다.
그리고 모델이 표현할 수 있는 것은 기획이 반드시 쓴다.

> 표현력 확장의 올바른 질문은 "모델이 감당하냐"(항상 예)가 아니라
> **"세 소비자 중 누가 감당하고, 감당 못 하는 쪽은 그 사실을 어떻게 정직하게 드러내는가"**다.

## 7. 목표 장르 대비 갭 분석

### 이미 커버되는 것

- **일본식 플래그 분기의 90%** — 조건이 노드가 아니라 **간선**에 있으므로
  "같은 목적지로 가되 조건이 다른 길"이 자연스럽다.
- **브란테식 스탯 체크** — `Stat + GreaterOrEqual + HideWhenLocked=false + LockedReasonText`.
  잠긴 선택지를 회색으로 보여주며 이유를 말해주는 것, 브란테가 실제로 하는 것.
- **`VisibleConditions` / `Conditions` 분리** — "안 보임"과 "보이지만 잠김"은
  완전히 다른 연출이다. 한 필드로 합쳤다가 나중에 쪼개는 팀이 많다.
- **bool을 0..1 Number로 눌러둔 것(§G4)** — 별도 타입을 안 만들어 분석기가 단일 경로.

### 비는 것 다섯

| # | 갭 | 영향 장르 | 비고 |
| --- | --- | --- | --- |
| 1 | **회차 계승 상태 없음** | 일본식 VN | **가장 큼.** "세이버 루트를 봐야 UBW가 열린다"는 계정 단위 상태. `ConditionKind.EndingSeen`/`GlobalFlag` 부재 |
| 2 | **`NotExists` 없음** | 일본식 VN | "그 에피소드를 아직 안 봤으면"을 표현 못 함 |
| 3 | **방문 횟수 없음** | 텍스트RPG | `ClearedEpisodeIds`가 집합이라 재방문 횟수를 셀 수 없다 |
| 4 | **스탯 간 비교 없음** | 브란테식 | `trust > suspicion` 불가. 대립 스탯 구조에서 아쉬움 |
| 5 | **난수 없음** | 텍스트RPG | 주사위 판정. 코어는 의도적으로 결정적 |

## 8. 발전 방향성

### 즉시 — 스키마를 건드리므로 지금 결정

- **계승 상태의 소유권.** `ProgressionState` 밖에 계정 단위 `MetaProgression`을 두고
  평가기가 둘 다 읽는 구조. `ConditionKind.EndingSeen` 예약.
  나중에 넣으면 세이브 스키마와 상태 소유권이 전부 흔들린다.
- **`ClearedEpisodeIds` → `Dictionary<string,int> VisitCounts`.**
  `Exists`는 `count >= 1`의 특수 경우이므로 **상위 호환**이고,
  정수 스탯과 같은 구간 전파를 그대로 쓴다. 지금 하면 SchemaVersion 2 한 번으로 끝난다.

### 단기 — 분석을 깨뜨리지 않는 확장 (Tier 1)

- **`NotExists` 연산자.** bool 도메인이라 구간 전파가 안 깨진다. 그냥 넣으면 된다.
- **asmdef로 순수성을 규율에서 컴파일 에러로 승격.**
  유니티 참조 없는 별도 asmdef로 잠그지 않으면, 6개월 뒤 급한 밤에
  누군가 `Debug.Log` 하나를 넣고 그걸로 끝난다.
  더 세게는 별도 `.csproj` → DLL 또는 UPM 패키지.
  Avalonia와 공유하므로 어차피 그쪽이 자연스럽다.

### 중기 — 분석 불가 표현력의 격리 수용 (Tier 2)

- **OR** — 우선 **간선 복제로 버틴다**(OR = 간선 2개).
  저작 부담은 늘지만 분석이 산다. AND-of-OR 중첩이 정말 필요해질 때 재고.
- **스탯 간 비교 / 확률 간선** — 도입하되 해당 간선은 도달성 분석에서
  `UnreachableCause` 대신 **`Unknown`**으로 표시.
  툴이 "이 챕터 검증 커버리지 78%"를 노출한다.
  기획자가 무엇을 포기하는지 알면서 쓰게 하는 편이,
  "다 되지만 아무것도 검증 못 하는 스크립팅 언어"보다 훨씬 낫다.
- **난수** — 시드를 `ProgressionState`에 담고 **순수 PRNG를 코어 안에서** 굴린다.
  그래야 "세이브 + 시드"로 버그가 재현된다.
  `UnityEngine.Random`을 쓰는 순간 지금까지 지킨 것이 전부 날아간다.

### 검증 — 설계보다 먼저

**실제 작품 한 챕터씩을 이 모델로 포팅해 볼 것.**
브란테 1막 / 일본식 VN 한 장 / 텍스트RPG 한 챕터. 스프레드시트로 충분하다.
못 쓰는 것이 두세 개 나오고, **그게 진짜 갭 목록**이다.
위 우선순위는 상상이고, 포팅 결과가 실측이다. 일주일이면 답이 나온다.

### 성장 규칙 한 줄

> 표현력을 넓히되, 넓힐 때마다
> **"세 소비자(런타임·로더·분석기) 중 누가 감당하고,
> 감당 못 하는 쪽은 그걸 어떻게 정직하게 드러내는가"**를 표로 채우면서 넓힌다.
> 이 질문에 답 못 하는 확장은 보류.

### 경고 — 저작 UX는 하나가 아니다

세 장르를 하나로 만드는 건 **진행 모델**로는 가능하지만 **저작 UX**로는 아니다.
일본식 플래그 분기를 쓰는 작가와 텍스트RPG 스탯 밸런싱을 하는 기획자는
같은 화면을 원하지 않는다. Avalonia 툴이 뷰를 두세 벌 갖게 될 가능성이 큰데,
**그건 괜찮다** — 코어를 이렇게 빼놨으니 뷰만 늘어나지 판정 로직은 안 갈라진다.
애초에 이 분리가 값을 하는 지점이 정확히 거기다.

## 9. 이 구조로 얻은 것

1. **버그 재현 비용의 붕괴.** "세이브 + `Resume`"이 곧 재현.
   QA가 세이브 하나 던져주면 끝나는 팀과 재현 영상을 찍는 팀의 차이는 수십 배.
2. **"툴과 런타임이 어긋나는" 사고 클래스의 제거.** 발생 자체가 불가능.
3. **기획 변경 앞에서 협상 테이블에 올릴 물건.**
   "이건 지금 되고, 이건 스키마를 지금 고쳐야 하고, 이건 검증 커버리지를 포기하는 비용"을
   코드 근거로 즉답할 수 있다. 요구가 흔들리는 시기에 이 답변 능력은 아키텍처보다 값이 나간다.
4. **콘텐츠 QA를 사람에서 기계로 옮길 발판.**
   분기가 복잡해지면 도달 불가 엔딩을 사람이 플레이로 찾는 건 불가능해진다.
   그 시점에 가치가 선형이 아니라 계단식으로 뛴다.
5. **세이브 호환성 부채의 선불 상환.** P3 + D4.
6. **수정 위치가 항상 명확.** "모든 것에 주인이 하나."
7. **유니티발 리스크의 무풍지대.** 엔진 업그레이드·Domain Reload·IL2CPP가 코어를 스치지 못한다.
   덤으로 재생기를 하나 더 붙일 자유가 공짜.
8. **사고 과정의 박제.** 온보딩 자산이자, 6개월 뒤 "내가 왜 이랬더라"에 쓸 시간의 절약.

> **단, 이 장점 대부분은 아직 미수금이다.**
> 선형 VN에 머물렀다면 과투자였을 것이다.
> 지금 기획이 정확히 복잡한 분기 쪽으로 움직이고 있으므로,
> 투자를 잘한 게 아니라 **회수 국면에 정확히 걸린** 것이다.
> 실제 작품 한 챕터를 포팅해 "된다"를 증명하는 순간 미수금이 현금이 된다.

## 10. 이런 구조를 만드는 경우와 실제 사례

### 만드는 네 가지 트리거

1. **같은 판정을 두 곳 이상에서 돌려야 할 때** — 툴+런타임, 클라이언트+서버, IDE+컴파일러
2. **재현성이 돈일 때** — 리플레이, 버그 재현, 규제 감사
3. **규칙을 실행 전에 검증하고 싶을 때** — 규칙이 코드면 실행해봐야 알지만 데이터면 분석할 수 있다
4. **도메인 수명이 프레임워크 수명보다 길 때** — 오래 사는 쪽을 짧게 사는 쪽에서 떼어낸다

### 패턴 이름

- **Functional Core, Imperative Shell** (Gary Bernhardt) — 가장 정확히 일치
- **헥사고날 아키텍처 / Ports & Adapters** — 넓은 계열
- **Sans-IO** — 파이썬 진영의 명명

### 실제 사례

| 사례 | 대응하는 지점 |
| --- | --- |
| **Ink** (Inkle, *80 Days*) | 가장 가까운 친척. 순수 C# 런타임이 유니티·언리얼·웹에 붙고, 저작 툴 Inky가 그 런타임을 그대로 물고 미리보기. 상태를 JSON으로 직렬화해 어디서든 복원 |

| **Redux** | 타임트래블 디버깅이 가능한 이유 = 세이브 재현이 가능한 이유. 불변 상태 + 순수 전이 |

| **록스텝 / 롤백 넷코드** | Age of Empires, Factorio, GGPO. 입력만 주고받고 결정적으로 시뮬. 비결정성 한 톨이면 디싱크. Factorio 리플레이가 작은 이유 = P3와 같은 논리 |
| **Roslyn** | "판정기 공유"의 대규모 사례. 불변 신택스 트리 기반 순수 API를 컴파일러·VS·분석기·포매터가 공유 |
| **LMAX 매칭 엔진** | 결정적 순수 로직 + 이벤트 기록. 장애 복구와 규제 감사 재현. IO/스레딩은 바깥 껍질(Disruptor) |
| **hyper-h2 (Sans-IO)** | 프로토콜 상태 기계가 소켓을 모른다. 바이트를 넣으면 이벤트가 나오고 보낼 바이트를 값으로 내놓는다. 동기·asyncio·trio 어디에나 붙는다 |
| **보험 심사 / 대출 승인 룰 엔진** | 규칙이 데이터인 이유가 같다. "어떤 조건으로도 승인 불가한 신청자"와 "어떤 경로로도 도달 불가한 엔딩"은 같은 문제 |

### 공통 본질

> **"결정과 실행을 가르고, 결정 쪽에서 시간과 세계를 추방한다."**

게임은 디싱크 때문에, 금융은 감사 때문에, 워크플로는 복구 때문에,
컴파일러는 툴 공유 때문에 — 출발 동기는 전부 달랐는데 도착지가 같다.
서로 다른 산업이 독립적으로 같은 형태에 수렴했다는 건,
이것이 유행이 아니라 **문제 자체의 구조가 강제하는 답**이라는 뜻이다.

이 맥락에서 `Ked.Progression`이 무엇인지 다시 말하면:
**내러티브 진행이라는 도메인에 대한 sans-IO 결정 코어**다.
Ink가 대사 층에서, Temporal이 업무 층에서 한 것을 진행 층에서 한 것이다.

## 부록 A. 동료 개발자용 온보딩

### 세 문장 소개

> 이건 **진행(progression) 결정 기계**다. 유니티도, 파일도, 시간도 모른다 —
> 대사·연출·저장을 전부 이름과 값으로만 주고받고, 우리가 바깥에서 펌프를 돌린다.
> 그래서 런타임과 Avalonia 툴이 **문자 그대로 같은 static 함수**로 판정한다.

### 동작 원리

> 코어는 아무것도 부르지 않는다. `Pending`에 "지금 대사 X를 틀어줘"를 값으로 내놓고 멈춘다.
> 다 틀고 나서 완료 메서드를 불러주면 다음으로 간다.
> 콜백도 이벤트도 async도 없으니 스레드·생명주기 문제가 코어에 존재하지 않는다.

### 읽는 순서

```
ProgressionCondition   →  조건이라는 원자
EpisodeOption          →  간선. 조건과 효과의 주인
EpisodeNode            →  노드. 엔딩키의 주인
ChapterTransition.Resolve  →  판정
EpisodeFlow            →  흐름과 경계
ProgressionSave        →  영속화
```

### 만질 때의 금칙 4

1. `using UnityEngine`을 추가하는 순간 이 패키지의 존재 이유가 끝난다.
2. 안쪽 함수에 null 체크를 넣고 싶어지면 **코드를 고치지 말고 멈춰라** —
   그건 경계가 샜다는 신호다(P2).
3. 세이브에 필드를 추가하고 싶으면 먼저 **"이게 상태냐 해석이냐"**를 물어라.
   재계산 가능한 건 넣지 않는다(P3).
4. `FlowRequestKind`에 여섯 번째를 추가하는 건 경계면 확장이다. 혼자 결정하지 않는다.
